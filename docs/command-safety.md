# Command Safety

## Hard Rules

- Never delete files automatically on a `guarded` server.
- Never change firewall rules automatically.
- Never reboot automatically unless explicitly approved.
- Never edit OpenVPN, SSH, Docker, or system configuration files without approval.
- Never expose ports automatically.
- Never run unlogged arbitrary shell commands generated by an LLM.
- Never place an OpenAI API key or other controller secret on a managed server.
- Never install or replace server scripts without explicit user approval.

## Allowed Execution Model

Mutating server-side commands must be represented by predefined action IDs in the controller action registry. Action execution is implemented only for explicitly supported actions.

An LLM or Codex may recommend an action, but executable actions must map to a local controller definition:

```text
recommendation -> action_id -> registry lookup -> policy check -> approval check -> execution
```

Free-form commands from an LLM response are advisory text only and must not be executed against servers.

Inventory access profiles set the future authority boundary:

- `guarded`: predefined action IDs only.
- `experimental`: future logged admin commands may be allowed after approval.
- `lab`: future arbitrary logged admin commands may be allowed after approval.

For the current read-only collection phase, the inventory `remote_health_command` is allowlisted. The only approved v1 remote health command is:

```text
/opt/homeops-agent/server-scripts/common/health_summary.sh
```

Changing `config/servers.yaml` to a different command string should fail before SSH execution.

## Risk Levels

### read_only

Allowed by default.

Examples:

- collect health summary
- check disk usage
- check service status
- check update counts
- inspect Docker container status

### low_risk

May be allowed automatically only if policy explicitly enables it.

Examples:

- refresh apt package metadata
- collect a journal summary
- run a non-mutating Docker inspection command

### approval_required

Requires explicit human approval every time.

Examples:

- deploy the approved health script
- restart a service
- restart a Docker container
- apply security updates
- prune Docker images or build cache
- reboot a server

### forbidden

Must not be exposed through the controller for `guarded` servers. Destructive
work on `experimental` or `lab` servers belongs in an explicit rebuild/admin
mode with action history and a before-state report.

Examples:

- recursive deletes
- firewall rule changes
- SSH configuration edits
- OpenVPN configuration edits
- Docker daemon configuration edits
- unlogged arbitrary shell command execution
- automatic port exposure

## Sudoers Profiles

The repo includes profile templates under `server-scripts/sudoers/`.

- `guarded.sudoers.template`: narrow maintenance commands.
- `experimental.sudoers.template`: narrow commands now, with a documented path
  to future broad sudo after logging exists.
- `lab.sudoers.template`: intentionally broad `NOPASSWD: ALL` for disposable lab
  machines.

Install sudoers manually with `visudo`. Do not store sudo passwords or private
keys in the repo.

## Approval Standard

Approval must be specific. A valid approval identifies:

- server ID
- action ID
- key arguments
- known risk

Example:

```text
Approve action restart_docker_container on container-host with container watchtower
```

The controller also supports exact approval phrases for implemented actions. A
dry run prints the phrase that must be supplied before execution:

```powershell
python -m controller.main actions run restart_docker_container --server container-host --container watchtower --dry-run
```

The corresponding approval phrase is:

```text
Approve action restart_docker_container on container-host with container watchtower
```

Service restarts use the same exact approval model and accept only approved
unit names for the target server role. Examples:

```powershell
python -m controller.main actions run restart_service --server ispy-server --service AgentDVR.service --dry-run
python -m controller.main actions run restart_service --server openvpn-server --service openvpnas.service --dry-run
python -m controller.main actions run restart_service --server container-host --service docker.service --dry-run
```

The controller normalizes approved aliases such as `openvpnas` to
`openvpnas.service`, but it does not accept arbitrary service names.

Health script deployment is also approval-gated and only copies the known
repository script to the approved remote path:

```powershell
python -m controller.main actions run deploy_health_script --server container-host --dry-run
```

The corresponding approval phrase is:

```text
Approve action deploy_health_script on container-host
```

Security updates are approval-gated and use the managed server's
`unattended-upgrade` policy:

```powershell
python -m controller.main actions run apply_security_updates --server openvpn-server --dry-run
```

The corresponding approval phrase is:

```text
Approve action apply_security_updates on openvpn-server
```

Server reboot is approval-gated and schedules a one-minute delayed reboot:

```powershell
python -m controller.main actions run reboot_server --server ispy-server --dry-run
```

The corresponding approval phrase is:

```text
Approve action reboot_server on ispy-server
```

## Audit Trail

Every action attempt should write an action history record containing:

- timestamp
- server ID
- action ID
- arguments
- risk level
- approval source
- command or script path executed
- exit code
- stdout summary
- stderr summary

Action records are stored under:

```text
history/actions/
```

The HTML dashboard loads these records so dry-runs, approval denials, completed
actions, and failed actions remain visible during normal review.

## Script Deployment

The current implementation can deploy the approved health script through the
`deploy_health_script` action. The action:

- copies only `server-scripts/common/health_summary.sh`
- targets only `/opt/homeops-agent/server-scripts/common/health_summary.sh`
- sets executable mode with `chmod 755`
- writes action history
- requires exact approval before execution

It must not copy arbitrary generated commands or mutate system configuration.
